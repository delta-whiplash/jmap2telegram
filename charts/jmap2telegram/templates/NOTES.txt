jmap2telegram is deploying.

The bot works by long-polling the Telegram Bot API outbound: nothing needs
to be exposed to the outside, and by default no Service is created. The
container still listens on port 8080 ("health"), where it serves the
kubelet probes (/healthz, /readyz - the kubelet reaches the pod directly,
no Service involved) and /metrics in Prometheus text format.

{{- if .Values.metrics.service.enabled }}

metrics.service.enabled is on: a cluster-local Service,
{{ include "jmap2telegram.fullname" . }}-metrics, exposes port 8080 for
in-cluster scraping:
  kubectl get service {{ include "jmap2telegram.fullname" . }}-metrics -n {{ .Release.Namespace }}
  kubectl port-forward service/{{ include "jmap2telegram.fullname" . }}-metrics 8080:8080 -n {{ .Release.Namespace }}

If your scraper relies on annotation-based discovery, remember to opt the
pod in via podAnnotations (prometheus.io/scrape, prometheus.io/port,
prometheus.io/path - see the example in values.yaml).
{{- else }}

metrics.service.enabled is off, so port 8080 stays reachable only by the
kubelet. To scrape /metrics from inside the cluster, redeploy with:
  --set metrics.service.enabled=true
{{- end }}

Check it came up:
  kubectl get pods -l app.kubernetes.io/instance={{ .Release.Name }} -n {{ .Release.Namespace }}
  kubectl logs -l app.kubernetes.io/instance={{ .Release.Name }} -n {{ .Release.Namespace }} -f

Then open Telegram, start a chat with your bot, and send /start from one of
the chat ids listed in telegram.authorizedChatIds.

Don't know your chat id yet? Telegram never shows the numeric id the bot
needs anywhere in its UI, and the bot can't tell you either - it refuses
to talk to anyone not in the allowlist. Send it anything (/start works)
anyway: the bot logs the refused chat id at WARN level, so you can read
it with:

  kubectl logs -l app.kubernetes.io/instance={{ .Release.Name }} -n {{ .Release.Namespace }} | grep "unauthorized access attempt"

(or just ask @userinfobot in Telegram for your id). Put the number in
telegram.authorizedChatIds and redeploy - the full walkthrough lives in
the "Finding your Telegram chat id" section of the project README.

{{- if not .Values.persistence.enabled }}

⚠️  persistence.enabled=false: connected JMAP accounts will be lost on every
    pod restart, and everyone will need to /login again. Fine for a quick
    test, not recommended otherwise.
{{- end }}
